# Digital Harinezumi 2++ 日光彩色研究版 v0.3

第一台研究对象是 SuperHeadz Digital Harinezumi 2++。本轮只研究彩色、ISO 100、远景条件下的图像性格，Android 中显示为 **DH 2++**。这是依据公开样片制作的近似模型，尚未通过同场景实机照片标定；所有传感器、镜头与 ISP 数值都是工程假设。

## 依据与边界

- [2++ 实拍评测](https://hendigi.com/digital-harinezumi-2-double-plus/)：区分彩色与黑白、ISO 100 与 800，作为本轮限定型号和拍摄条件的主要依据。
- [2++ 使用者后续实拍](https://hendigi.com/digital-harinezumi-again/)：观察红、绿、蓝物体的浓郁颜色、柔软细节，以及高反差场景中的明暗取舍。
- [Harinezumi 2 评测](https://blindlight.wordpress.com/2010/08/10/superheadz-digital-harinezumi-2-review/)：仅作同系列背景资料，不能用它证明 2++ 的精确参数。

网页中的缩图、压缩、曝光选择与后期处理都可能影响观感。没有下载或打包他人照片；原作者的照片也不属于本项目的 MIT 授权内容。

## 本轮实现

| 观察方向 | 实现 | 尚未证明的部分 |
| --- | --- | --- |
| 浓郁原色与较深中暗部 | 独立颜色矩阵、轻微暖白平衡、较陡的色调曲线 | 色相响应与真实相机吻合度 |
| 高亮容易失去层次 | 较短的高光过渡和传感器饱和 | 实机曝光、动态范围、场景自适应行为 |
| 柔软细节 | 空间变化 PSF、去马赛克、轻度降噪与低锐化 | 实机 MTF、对焦距离与镜头个体差异 |
| 日光下适度电子噪声 | 信号相关散粒噪声、读出及固定模式噪声 | 实测 ISO 100 噪声分布 |
| 早期数字照片的有限细节 | 优先 4:3 输入、最高 320 万像素输出，不放大较小输入 | 320 万是本轮输出策略，不能当作已核实的该型号传感器规格 |

相机继续使用手机的自动曝光与自动对焦，EXIF 记录手机实际 ISO、曝光时间和镜头信息。研究范围中的 ISO 100 不会冒充照片实际 ISO。保留原有四款风格；首次安装默认 DH 2++，升级保留已保存的选择。

v0.2 将 PSF、ISP 滤波尺度和噪声功率换算到同一参考尺寸，但仍不是完整的固定虚拟传感器采样。输出像素上限也不等于已实现真实低分辨率传感器。自动白平衡跳变、远景/微距拨杆、JPEG 编码性格、机身操作体验和 ISO 800 均不在本轮复刻范围内。

## 可重复比较

安装项目 Python 依赖后，在仓库根目录执行：

```bash
PYTHONPATH=reference python3 tools/render_camera_study.py --output-dir renders/dh2-chart
PYTHONPATH=reference python3 tools/render_camera_study.py --input /absolute/path/daylight.jpg --output-dir renders/dh2-photo
```

工具输出同尺寸的原图、DH 2++ 彩色 v0.4、DH 2++ 黑白 v0.2 及并排对照图，并记录输入与配置的 SHA-256、尺寸、随机种子。默认没有输入时使用合成测试图，它只用于检查信号行为，不能证明实机还原度。输入照片应为 sRGB，输出目录必须尚不存在，以保留先前的比较记录。

## 验证与下一步

新增测试检查灰阶次序、中间调可用性、原色分离、边角亮度、随机种子重复性、发布包与 JSON 一致性，以及 Python/C++ 五阶段数值一致性。冻结了独立的 v0.1 回归清单。原生测试强制启用 assert，避免优化构建把检查编译掉。

Android 编译与 lint、上述自动测试负责证明工程行为；真实相机还原度仍需成对样片验证。下一轮优先拍摄同场景的红色物体、绿色植被、肤色、天空和背光高亮，先校正色彩与曝光响应，再决定是否需要新增引擎能力。

### v0.2：预览与成片尺度换算（2026-09-10）

本轮保留 v0.1 配置与回归清单，新增独立的 v0.2 配置；Android 0.11.0 的 DH 2++ 使用新版。其他风格没有 `reference_sampling` 字段，继续采用原行为。

- 参数参考尺寸为 1920×1440，属于工程参数坐标，不是实机传感器规格。
- PSF 核按宽高比例投射并保持能量，降噪与锐化半径按几何平均比例换算。
- 噪声换算考虑双线性 CFA 插值产生的像素相关性；散粒、读出、固定模式及行列噪声分别处理，同时保持信号增益和饱和点。
- Python、C++ CPU、Android Vulkan 共用同一换算规则；不改变输入输出尺寸、Camera2 曝光或 EXIF。
- 超过参考尺寸两倍或共享滤波支持范围（9×9 PSF、有效 Gaussian sigma ≤ 1）的请求会明确失败，避免不同后端静默使用不同滤波范围。

复现完整尺寸诊断：

```bash
PYTHONPATH=reference python3 tools/check_resolution_consistency.py --profile-version 0.2 --width 1920 --height 1440 --factor 3 --output-dir renders/dh2-resolution-check
```

本地 `renders/harinezumi_2pp_v0_2/scale_3/metrics.json` 记录的结果：

| 合成测试指标 | 原规则 | v0.2 |
| --- | ---: | ---: |
| 640×480 预览 / 缩小后成片的时间噪声标准差比值 | 1.4602 | 1.0231 |
| 噪声强度偏差 | 46.02% | 2.31% |
| 无噪声条纹信号的预览/缩图 RMSE | 0.0007462 | 0.0006408 |

灰片噪声用两帧差分隔离，不把暗角或固定色偏误算成噪声；条纹测试只检查细节响应。这些结果不能推广成所有实拍场景的改善百分比。当前 Bayer 采样格、去马赛克、主机处理以及预览显示缩放仍可能引入差异，不能保证逐像素一致。

本轮已通过原生测试、53 项 Python 测试和 Android debug 构建/lint。早期 0.11.0 试包已在上一工作阶段安装到 SM-S9210；2026-09-10 继续验证时 ADB 未检测到设备，最终 APK 尚未重新安装，因此新版实时性能、拍摄保存及 GPU 数值一致性验证仍待实机补齐，不能沿用 v0.1 的实机数据作为 v0.2 验收结果。

正文出处：[2010 2++ 评测](https://hendigi.com/digital-harinezumi-2-double-plus/)及[2025 再次使用 2++](https://hendigi.com/digital-harinezumi-again/)。室内光源、曝光、白平衡、缩图与压缩都可能影响观感，以上现象不能直接反推出相机参数。

实现限定在 v0.3 的白平衡、颜色矩阵和暗部/中间调曲线。传感器噪声参数、光学核、参考尺寸以及 v0.2 的尺度换算保持原值，v0.1/v0.2 文件保留。Android 0.12.0 的 DH 2++ 切换到 v0.3。

合成诊断中，固定底色 0.16、主通道从 0.3 到 0.95 的渐变，经渲染后中心区域大于 0.995 的比例：红色从 22.54% 降至 12.77%，蓝色从 5.05% 降至 0.75%。这证明预设减少了过早饱和，不是与网页照片相似度的评分。0.45 灰阶的通道差也缩小，零输入依旧为黑。

验证：原生测试、58 项 Python 测试、Android `assembleDebug` / `lintDebug` 通过。新增测试覆盖色阶截断、暗部、黑位、中性色、发布包和 C++ 输出一致性。生成对照图位于 `renders/harinezumi_2pp_v0_3/`，均为合成测试图；本轮没有实机样张或真人肤色验收。


### 2026-09-30：黑白研究版与风格选择 UI（Android 0.13.0）

依据[再次使用 2++ 的文章](https://hendigi.com/digital-harinezumi-again/)中确认的彩色/黑白切换功能，新增独立 `toy_harinezumi_2pp_mono_v0_1` 配置。此次网页正文可读取，但图片加载失败，因此黑白参数属于设计近似，未完成逐图观察或同场景拟合。作者没有逐张标明黑白样片 ISO，本版不据此推断 ISO 800。

引擎新增可选 `isp.monochrome` 布尔字段，默认关闭。在镜头、传感器、去马赛克、白平衡、颜色矩阵及滤波后，以 Rec.2020 线性亮度权重混合为单通道，再应用专用曲线和 sRGB 编码。Python、C++ CPU、Vulkan 采用同一顺序；Vulkan 继续使用现有 ISP pass。黑白输出三通道完全相同，噪声来自传感器模型。光学与传感器参数沿用彩色研究版的假设，输出仍采用 4:3 与 320 万像素上限策略。

UI 加大风格按钮到 48dp 高，支持内容宽度，显示当前风格说明，并在选择后滚动至当前项。标题直接显示相机风格名，版本保留在成片元数据中。修复拍摄结束后快门需要等待下一次就绪回调才能重新启用的问题。

本地原生测试与 66 项 Python 回归通过，包含黑白噪声重复性、无色度输出、灰阶次序、配置包一致性和五阶段 CPU/参考一致性。Android debug 构建、Vulkan shader 编译与 lint 通过。合成对照图和实机截图保存在 `renders/harinezumi_mono_v0_1/`；这些检查负责验证工程行为，未证明与真实 Harinezumi 的成像吻合度。


实机验证：测试版已安装到已连接 Samsung SM-S9210，成功拍摄并保存 1440×1920 黑白 JPEG，回看与返回相机正常，返回后的快门可用。成片最大 RGB 通道差为 0。现场镜头信号很暗（8-bit 最大值 3），本次成片只验证保存、元数据与无色度输出，不作为影调验收图。EXIF 保留手机实际 ISO 7227 与曝光约 0.0399 秒。检查发现中文风格名在 ASCII EXIF 字段中被替换为问号，已将 Software/ImageDescription 改为稳定风格代码；界面与回看仍使用本地化名称。

短时预览日志记录 660 帧渲染/提交/零拷贝/显示、0 引擎错误，滚动 P95 为 23.98 ms，同时有 81 队列丢弃，设备处于温控降帧状态。此处记录真实观测，不作为无丢帧或长期性能验收。


### 2026-09-30：样片细节、预览清晰度与 UI（Android 0.14.0）

此次实际查看了作者公开发布的九张 800×600 缩图，包括红椅 PICT0015、黄色滑梯 PICT0017、圈形滑梯 PICT0019、河岸 PICT0021、室内 PICT0010/0011，以及黑白 PICT0009/0007/0006。仅用于观察；照片没有进入应用资源或配置包，也没有把已经成像的网页样片再次送进引擎冒充场景输入。

观察与调整：红色座面保留渐变，地面有纹理；滑梯与天空容易截断；河岸的暖建筑、青蓝天空和橄榄绿植被共存；黑白自行车车架和树木暗部仍有中间灰。因此彩色 v0.4 保留 v0.3 的矩阵、白平衡和曲线，将 Gaussian 降噪从 0.42 降至 0.32、锐化从 0.06 调至 0.10。黑白 v0.2 同时缓和暗部和中亮部曲线，白点由 0.88 延至 0.92。参数仍是设计假设，网页缩图没有同场景手机原图，不能作为硬件标定或相似度评分。

预览原先明确优先 640×480：旋转后短边 480 像素，先放大到 720 宽 Surface，再放大到屏幕。此时 Bayer 再采样/去马赛克仍消耗固定像素细节，PSF 分数坐标离散也引入额外方差，单靠 profile 尺度换算不能恢复已丢失的信息。本版将预览目标设为 1280×960，尺寸边界为 1440×1080/160 万像素，选择与成片匹配的比例；显示缓冲随实际取景大小，最大宽 1080，取消固定 720 中间放大。手机支持的 FAST 边缘、降噪和色调模式在 PREVIEW/STILL_CAPTURE 两种请求中统一，减少默认模板处理差异。

UI 将顶部 84dp、底部 182dp 与系统 Insets 留给操作；取景区域在独立容器中按成片比例居中，避免控件覆盖画面。风格使用文字轨道与短下划线，缩略图、快门、切换图标和信息行统一；回看照片也位于独立区域。

新增 `tools/check_preview_detail.py` 用合成斜边、线对和棋盘比较同显示尺寸的预览/成片。默认 384×288 模型保留 1920×1440 各档的比例，关闭噪声；报告 Python 参考渲染结果，不冒充实机 GPU 或真实相机 MTF。原生 Surface 模型斜边 MTF50：参考成片 0.2134，640 预览 0.0892，1280 预览 0.1511，1440 预览 0.1769 cycles/display-pixel。720 中间 Surface 会再降低边缘响应；RMSE 在部分高频信号可能奖励平滑，不能独立当作清晰度评分。结果位于 `reports/preview_detail_20260930_native_surface/` 与 `reports/preview_detail_20260930_720_surface/`。

复现：

```bash
PYTHONPATH=reference python3 tools/check_preview_detail.py --output-dir /tmp/preview-native
PYTHONPATH=reference python3 tools/check_preview_detail.py --surface-short-edge 720 --output-dir /tmp/preview-720
```

提高输入分辨率会减轻固定像素去马赛克与 PSF 离散差异，但仍不能保证预览与不同手机成片逐像素相同。手机自身缩放、主机 ISP、曝光/对焦和屏幕显示均可能造成差异。当前 Vulkan 锐化低通和 Python/CPU 的降噪顺序还存在小差异；本轮不将 Python 合成工具当作 Vulkan 精确一致性证明。


性能策略：90 帧启动阶段之后，每 3 秒参考滚动预览 P95，以 10% 余量选择 30/24/20/15/12/10/8/5 FPS 档；SDK 的 `setPreviewFrameRateBudget` 与温控上限取较小值，Camera2 请求随之更新。该策略保留输入分辨率，减少处理能力不足时的队列丢弃。拍照期间不更新预算，暂停与风格切换会重置预算。较热或较慢设备可能使用较低帧率。


实机验证（SM-S9210）：Android 0.14.0 的实际 PRIVATE 预览为 1440×1080，取景为 1046×1394 像素，显示缓冲 1046×1395（按3:4整像素取整）。布局检查确认取景边界在顶部355到1749像素之间，避开顶部和底部操作区。D01 在初始24 FPS条件下滚动P95约37 ms；DH 2++ 在Moderate温控下P95约75 ms，自适应预算为12 FPS，Camera2支持的范围为15–15，因此多余帧在节奏入口主动跳过。DH会话中，420到720渲染帧间队列丢弃保持3，提交/零拷贝/显示帧数一致，0引擎错误、0swapchain重建。这是短时观测，不是长期性能或多机型验收。

最终版 DH 2++ v0.4 已成功保存1440×1920 JPEG，3A收敛后提交，保存日志确认连续预览恢复。真实场景为近距离笔记本屏幕/键盘，不能用它证明与网页日光场景的色彩还原度。实机日志、照片和布局截图位于 `renders/preview_detail_v0_14/`。原生测试、76项Python回归、Android debug构建与lint均通过。
